Client work, described

Four problems from nine years on healthcare products, told as decisions rather than deliverables. I can walk you through the real interfaces on a call.

The loader that was never a loader

Telehealth platform for substance-use treatment. React and React Native. I built its UI from zero and owned it for four years.

Patients said the onboarding chatbot moved on before they could read each question. The obvious fix was a slower animation. I fixed the cause instead: pacing now comes from the length of each question.

Read the case study
The problem

Between assessment questions, a loading animation played for a fixed time. The questions vary from one line to a short paragraph, so any fixed duration is too slow for short ones and too fast for long ones. Slowing it down would have traded one complaint for another.

What I did

Nothing was actually loading: it was a reading pause dressed up as a loader. A reading pause should depend on how much there is to read, so I stopped storing a duration at all. I wrote the timer logic in the product code myself: a reading-speed constant multiplied by the rendered line count of the question on screen.

What happened

Every questionnaire got the right pacing, including ones written later by people who never saw the ticket. There is no per-question setting for anyone to get wrong.

Making an argument physical

Electronic health record, mobile app. Usability testing.

Clinicians said the login fields were out of thumb reach. The team saw a balanced layout on a monitor, so I stopped arguing about it and put a prototype in their hands.

Read the case study
The problem

Clinical staff open the app one-handed while doing something else. A login they have to re-grip for is friction at the start of every session. In Figma, at eye level, the layout looked fine, so the feedback was read as a matter of taste.

What I did

With an external UX expert, I built a prototype you had to hold: the real interface, at real size, in one hand. That turned an opinion about a layout into a fact about a thumb.

What happened

The redesign shipped. The method is the part I reuse: when a disagreement is about a physical experience, show it in the medium where the problem is obvious.

Accessibility as a theme, not a checklist

Healthcare product in Angular. Three years owning its UI structure and components.

Instead of auditing screens one by one, I put contrast and type scale in the theme, then added three user-selectable themes for colour-vision deficiencies.

Read the case study
The problem

The product had to meet ADA expectations. My part was the visual layer: typography and colour. An audit only fixes the screens that exist on the day of the audit.

What I did

I set contrast ratios and the type scale in the theme, so every screen, including ones built later, gets compliant colour and type by default. Contrast helps people with low vision but not people who can’t separate two hues, so I also shipped themes for deuteranomaly, protanomaly and tritanomaly. Keyboard and ARIA behaviour came from the component framework; my job was not to break it.

What happened

QA and real users verified the themes. Accessibility could no longer regress quietly, and the product gained a feature for people the baseline standard doesn’t reach.

A design system is a product, not a file

Shared component library across several healthcare products. Angular, React, React Native and Figma.

Several products, three front-end stacks, and constant pressure to copy a component and tweak the copy. One rule kept the system whole: products change the theme, never the shared components.

Read the case study
The problem

When a shared component doesn’t quite fit, teams fork it. Do that enough and the design system becomes a folder of lookalikes, and a bug fixed in one place stays broken in four others.

What I did

I built a component library on Angular Material and MUI with a matching Figma library of components, variants, styles and variables. Because I maintain both the designs and the code, they can’t drift apart in a handoff. I also trained designers and UI developers on Git, so contributing to the shared library became normal work.

What happened

Bugs get fixed once, in the component, and every product inherits the fix. New screens start from parts that are already accessible, themed and consistent.

How I work

  • Fix it once, where everything inherits it

    Fix the component so every product gets the fix. Set contrast in the theme so every screen gets it. Compute the pacing so every question gets it. It’s the thread through all of my case studies.

  • I ship the front end myself

    I write the production React, React Native, HTML and Sass. Design intent survives implementation, I can judge feasibility in the conversation instead of after it, and I check the real build, not a mock-up.

  • Broken beats better

    I once opened a staging link on my phone at home, found the layout broken, and raised it at stand-up instead of quietly patching it. Then I made it properly responsive. Ranking work honestly matters more than protecting a plan.

  • Real users are my feedback loop

    I’ve run requirements interviews and usability tests, but my steadiest source of truth is people reporting problems in a live product, and folding each fix back into the components so it can’t recur.
